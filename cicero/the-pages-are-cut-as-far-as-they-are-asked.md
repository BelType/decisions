# The pages are cut as far as they are asked

**Status: Decided 2026-10-12, Executed 2026-10-12.** Ruled by Egildo in the `cicero-optimisation` round (plan item C4), the principle in his own words — *Cicero should support progressive pagination; when mounted in an application like the editing tools, a higher logic can tie it to the reader's scroll* — and the five questions of the design note (`.claude/plans/cicero-optimisation/progressive-display.md`) taken on the note's recommendations, 2026-10-12. It changes when a page is shown and not where any of them breaks.

## Context

The first page appeared in the same frame as the last, because the seam did three things in strict order: the whole run (`paginate`, up to three layouts where the document has forward page references), then the intake (the document moved into `<beltype-root>`), then `present()`. On BelType's manual the reader looked at an empty frame for the 2.4 s of the run, on the BGD manual for 0.45 s. The work did not need doing in that order: a Ledger entry closes a page and is the full resume state of the next (*the run resumes from an entry*, Decision one), so a run can stop at any page and go on from it, and a page is a Ledger interval the moment its closing entry exists.

**The principle: the engine offers a mechanism and the host chooses the policy.** The engine can cut the document as far as it is asked, present what it cut, keep its place and go on when asked again. When to ask — all at once, as far as the reader has scrolled, in idle time — is the host's question, because only the host knows what the reader is doing. The precedent is Word's background repagination; TeX's page builder is the older one.

**The rulings, taken on the note's recommendations, 2026-10-12.**

1. *Forward page references*: while the run is incomplete the reservation keeps its width and is painted invisible; the true number appears when delivered.
2. *The page total* (`counter(pages)`) is blank until known and then filled on every page at once. No estimate.
3. *Where delivered reads force a second layout*, the pages already on screen are replaced by the second layout's pages, the reader's place kept.
4. *The scroll extent* grows as pages are cut; no reserved estimated sheets.
5. *Policies*: the CLI preview cuts the first screen plus one, reveals, and continues to the end without pausing; the editing tools cut what the reader looks at and ahead of the scroll (windowing's viewport margin) and the rest in idle slices, so the document always completes, and a jump asks for its target first; print, Caster, the essay and the gates run to the end, unchanged.

And: `run()` with no `until` behaves exactly as today, and `pageOf` for an element not yet cut answers a distinct "not yet", not `null`.

## Decision

**`run({ until })` cuts as far as `until` and stops with its place kept.** `until` is a page count or a source element (the page that holds its first word). The answer says how many pages are cut and whether the document is `complete`. Called again on the same frame with a further `until`, or with none, the run goes on from where it stopped.

**The run is held, not re-entered.** The driver takes one option, `pace`, called after every page of the first layout with a `Progress` (the page count, the live account, the position index, `held(el)`, a `snapshot()` and the resumed run's `resumed`); a host that returns a pending promise has paused the page loop where it stands, with the measure context, the Ledger, the cursor, the composition and the read-ahead all kept in the closure, and one that returns nothing has asked for no pause. The alternative the note leaned on — continue by re-entering through the resumable run's machinery, with a prior Ledger and a restart page — was refused: re-entry pays the run-level setup again at every stop (the reads' site search, the forced-break index, the document ops: 460 ms on BelType's manual), which is exactly the cost the resumable run exists to pay once per edit, not once per slice. The resume machinery is used for what it is for: an edit.

**The intake moves before the first cut** (`root.intake`, which also parks the sources in the same call, because a slottable no slot takes answers no computed style). A run that can stop measures the sources while pages stand in the document, so it measures them where a resumed run always has. Fonts are awaited before the intake with a forced layout, since a document whose boxes are all parked lays nothing out and `document.fonts.ready` would resolve with the faces unrequested. A run that fails before it has shown a page puts the document back where it found it.

**Presenting between calls is an append.** The first stop presents the pages cut; each later stop adds the pages cut since (`present`'s resume form with an empty range before the new ones, which also reads the pages that stand again only when something about them could have moved); completion presents the rest and fills the total on every page at once. A document cut again whole (the second layout of a read) is replaced from the first page whose row differs (`firstDifference`), the pages before it kept. Pages added far below the reader ask no rectangle: they are the observer's. The dressing's one rule a measure cannot live beside (`break-before: auto !important`) is a sheet of its own and is left out for the whole run, because toggling it between two stops restyled every element under the root (about 5 ms a stop on the BGD manual, a third of the cost of stopping); the rest of the dressing, which is what a page looks like, stays in force.

**What is true only at the end waits for the end.** The page total is blank (`resolveContent`'s `pages: null`). A reserved page number is painted invisible (`visibility: hidden !important` on the pseudo-element that reads it, in a sheet of the engine's own, scoped to the presented document) until its true number is delivered, which the loop does the moment the layout it was cut in is complete; a read keyed by nothing (a literal `url(#x)` address) cannot be scoped and is left showing the reservation, a stated limit. `pageOf` answers `'not-yet'` for a place at or past the last page cut (a string, because the asking host lives in another realm as often as not); `reveal` returns false for it; a click on a link to a place not cut to waits for `run({ until })` and then follows, and so does an address typed into the bar (`root.cutTo`).

**An edit while the document is not complete** resumes within the pages cut: a stopped run's snapshot (`incomplete`) is the prior, the resumed run stays at the horizon it had unless `until` says otherwise, an edit beyond the horizon recuts the page before it and nothing else, and a resumed run that converges inside the pages cut keeps the pages after the converged one and goes on cutting from the last of them rather than ending.

**Refused.** Estimating the total or the extent (rulings 2 and 4). Hiding the reservation by changing its text — the measure and the presentation share the delivery sheet, and a different reservation would move the cuts of the first layout. Pausing in a layout the true page numbers sent round again (it is cut whole and shown afterwards: nothing paints between, so the replacement is seen only as the final pages). A time budget in the engine: how many pages a slice cuts is the host's, in pages, because a page count is what the engine can honour exactly.

## Consequences

**Measured 2026-10-12** in visible headless Chromium at 1400x1000 (Apple M1 Max, Chromium 153.0.8010.12), the CLI under `--engine cicero`, `.claude/plans/cicero-optimisation/bench/progressive-census.mjs`, the median of seven runs, the old and the new code run back to back on the same machine (milliseconds from navigation):

| Document | | first pages painted | document complete | pages first painted |
| :-- | :-- | --: | --: | --: |
| BelType's manual (280 pages) | before | 5 363 | 5 405 | 280 |
| | after | 3 383 | 5 178 | 2 |
| BGD manual (123) | before | 673 | 681 | 123 |
| | after | 287 | 711 | 2 |
| Plain text (33; 14 500 words) | before | 189 | 205 | 33 |
| | after | 191 | 208 | 33 (no pause: the whole run is under 100 ms) |
| Specimen (9) | before | 120 | 132 | 9 |
| | after | 116 | 136 | 9 |
| A 129-page document whose contents force a second layout | before | 1 176 | 1 196 | 129 |
| | after | 284 | 1 217 | 2 |

BelType's manual waits 2.26 s before `run()` starts (Mermaid and the compiler's client stages: a separate session) and the first view then takes 0.66 s, of which about 0.5 s is the run-level setup the first page cannot avoid (the stylesheet rewrite, the reads' site search, the document ops and the forced-break index); counted from the start of `run()`, 2 400 ms becomes about 660. Completion is not later: the manual's is 230 ms earlier, BGD's 30 ms later, the short ones' within noise.

**Cuts identical.** Every page's text after completion and `buildAll()` hashes the same before and after on the five documents (280, 123, 33, 9 and 129 pages), and the Ledger — the account as JSON, chrome included — is byte-equal across a straight run, a run stopped once at two pages, and a run stopped every three, five or seven pages, in the default mode and the composed, on the specimen, the BGD manual, the 29- and 129-page second-layout documents and the plain text (`bench/pause-identity.mjs`; `packages/essay/test/progressive.test.js` pins it in a venue).

**The cost of stopping.** A run stopped once costs nothing measurable in total (the BGD manual 459 to 524 ms against 450 to 545 straight in three runs, the manual 2 039 against 2 455, the same page cuts); one stopped at every page costs about 2 ms a stop beyond the cut itself on the BGD manual (a presentation of one page and the document laid out once more: 717 to 788 ms for 123 stops against 481 to 500 straight, with no yield between the calls), and cost 11 ms a stop before the dressing's break rule was taken out of the toggle. Nobody waits on a stop, but 123 of them are a quarter of the run again; the editing tools' slice is therefore 40 ms of cutting, not a page. **The total work is not the straight run's work**: parking the sources before the first cut makes every read of a source's style slower (the Stonehand's `adjudicate` 79 to 129 ms on the BGD manual, the forced-break index 30 to 44, the document ops 6 to 10, the manual's reads 139 to 214) and the measure's layout faster, because the document is no longer laid out behind the measure (the manual's `layout` 1 586 to 944 ms): the sum is 424 to 382 ms on BGD and 2 633 to 1 684 ms on the manual. The resumed run has always paid the slower reads; the first run now does.

**The second layout.** On the 129-page document (`bench/second-run-document.mjs`; the console says *settled in 2 runs*) the first view is painted at 284 ms with two pages whose contents entries are present and invisible (`visibility: hidden`, content `"0"`), then the run completes, the true numbers are delivered, the second layout is cut without a paint between, and the pages that differ are replaced — in the same frame as the completion — with the numbers visible (`"1"`, and the rest). Cuts identical to the straight run's.

**An edit while incomplete**, on a document stopped at three pages (`essay/test/progressive.test.js`): inside the horizon the run recuts from the page before the edit and stays at three, shows three, and going on to the end gives the Ledger a whole run over the edited document gives; beyond the horizon it recuts the one page before it (`resumed: { from: 3, to: 3 }`). The editing tools' edit loop on the BGD manual (eight edits, `bench-edit.mjs`, the median of the eight, four runs each side): keystroke to painted pages 301 and 269 ms before, 267, 301, 254 and 265 after; every edit on the patch road. The editing tools' first load of the same document shows its first pages at 1.5 to 1.7 s where it showed all of them at 3.2 s, and is complete at 2.6 to 2.8 s.

**Found along the way, not in the note.** (1) The measure context's container is one element for every context, and the presentation composes a page with a context of its own and puts it away, which removes the container from under a run that is waiting to go on: every measure now makes sure of the container, the neutralizing style and its own width first. (2) A stopped run's last row is complete, but its cut reads the boxes it pushed to the next page, which is why a resumed run restarts one page before and why the horizon edit recuts a page. (3) A forward read is not a layout fact the first view can show, so the hiding is by the pseudo-element and not by the value; BelType's own contents entry is one `::after` and is hidden whole. (4) `window.find` finds a word on the last page of the manual once the idle build has finished, and not before; that is the price the windowing record named, now paid for the whole document at the end rather than at the start.

**Owed, and none of it moves a cut.** (a) The break-neutralizing rule is in force only once the document is complete, so an author's `break-before: column` inside a multi-column box shows its break while the run is stopped and loses it at the end; no case has such a box. (b) A read keyed by nothing (`target-counter(url(#x), page)`) shows its reservation while the run is stopped. (c) The CLI pauses for a paint once, and only when the first view took 100 ms or more (a document whose whole run is a few frames is better shown whole: the frame cost the 33-page text a fifth of its time); it has no scroll-led pace, which ruling 5 did not ask of it. (d) `window.find` reaches a page once the idle build has built it, as the windowing record said; the end of the run now comes later than the first view, so the browser's find reaches the whole document later by as much.
