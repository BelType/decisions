# The second channel a named page cannot close

**Status: Decided 2026-08-26, Executed 2026-08-26.**

## Context

`packages/essay/cases/17-the-borrowed-dress` (two cases from a second stranger) found a real, unpredicted defect: a named `@page` rule's `content: normal` correctly clears `@bottom-center` (the folio) but does not clear `@top-center` (the running head) — the base rule's un-overridden string still prints on the title pages, and on ordinary pages `@top-center` prints doubled while `@bottom-center` prints correctly once. Filed on the checklist frontier ("A named page's `content: normal` override is honored for `@bottom-center` and not for `@top-center`"). The case is red by design, same posture case 15 held between the margin box leak earns a case and a page rule reads its own declarations.

Three independent readings this session ruled out every file that computes or writes margin-box values:

1. `capture.js`'s `readGeometryTable(doc).pageFor({name:'title', first:true, parity:'right'})`, probed directly and in isolation against the case's own live document, resolves BOTH `top-center` and `bottom-center` to `'normal'` — correct, before `resolveContent` ever runs.
2. `root.js` (the `present()` per-page loop, ~line 126-129) and `chase.js` (`BeltypePage`'s shadow-DOM cell construction and `setMarginBox`), read in full: zero name-based branching, one generic loop, one generic `cell.textContent = text ?? ''` write, fresh `<beltype-page>` elements rebuilt from scratch every `present()` call. `@bottom-center` working correctly through this exact code is proof by construction the fault is not here.
3. `driver.js`'s `paginate()`, read in full: `conditionsFor(pageIndex)` runs exactly once per page (`Object.freeze`d), `cursor.b` correctly holds across the title section's own 2-page continuation (both physical title pages resolve `name: 'title'`), no second/measurement pass over an already-built page, zero references to margin boxes anywhere in the file.

One unverified lead: `root.js`'s print pass (`#pressSheet`, `ensureDressingSheet`) renames every `<beltype-page>`'s CSS `page` property to a synthetic geometry name (`__bt-gN`) and injects `@page __bt-gN { size: ...; margin: 0; }`, but never removes, disables, or neutralizes the author's own original stylesheet — it stays linked throughout. Since no page is ever named `title`/`interlude` any more, only the author's base (unnamed) rule could still universally match every page through the browser's own native print engine — a second, independent rendering channel `chase.js`'s own header comment says should not exist ("an author's own stylesheet cannot reach a margin box... it does not live once, so it cannot live twice" — I6). If real, this explains both symptoms (title pages: shadow's correct `''` plus a native paint of the un-overridden base string, net one; ordinary pages: shadow's correct value plus the same native paint, net two).

**What this reading cannot explain**: why `@bottom-center` would be immune from a base-rule native paint that is, by this theory, unconditional and name-blind. Nothing found by reading source alone answers this. The one check that would tell a genuine Chromium-side cascade quirk (this document, printed with zero Cicero involvement, via `cases/runner.js`'s `printNative()`/`native.html`) apart from a Cicero-introduced defect was never actually run this session for the top/bottom asymmetry specifically — only for word-partition agreement, which is a different claim.

## Decision

Diagnose before fixing, per `cycle.md`. Run a live instrumented probe (reusing `packages/essay/lib/venue.js`'s `startVenueServer` and `@egildo/beltype-browser-chromium`'s `launchBrowser`, matching `cases/runner.js`'s own `printNative()`/`printLiveThroughCicero()` patterns) against the real `17-the-borrowed-dress` document, checking: whether `native.html` alone (zero Cicero) reproduces the asymmetry; the shadow-DOM cell's own `textContent` for both boxes on the title page, read directly; the live CSSOM `content` values for both boxes in both the base and `title` rules; the computed `page` property Chromium reports per `<beltype-page>`.

Depending on the outcome: if the leak is confirmed to come from a second, native-CSS-driven paint layer (the author's stylesheet still being live and matched), the fix is a small, surgically-scoped neutralization step — a new helper reusing `capture.js`'s existing `MARGIN_BOXES`/CSSOM-walk pattern that clears each captured margin-box rule's `content` (never its `size`/`margin`, never any non-`@page` rule) once `capture.js` has read what it needs, called once from `seam/client.js`'s `view()` before print. If instead `native.html` alone does not show the asymmetry, the diagnosis in this entry's Context is wrong at the root, and this entry closes without a fix, opening a narrower one instead of forcing a wrong theory's remedy onto a different cause.

**Refused: guessing the fix before the diagnostic runs.** Every prior fault in this family (the margin box leak earns a case→011, this session's own case 15/17) was earned by first watching the case fail for a reason it names — a case fixed in the same motion it was authored is a case nobody watched go red for the right reason.

## Predictions

Frozen on write, break-versus-hold decided in advance.

1. **The live diagnostic will show the shadow-DOM cell itself is correct** — `<beltype-page>`'s own `top-center` cell (title page) contains `''`, matching `capture.js`'s own resolution — and the visible leak comes from outside the shadow DOM. *Breaks* if the shadow cell itself is found non-empty.
2. **Raw Chromium's own print of the untouched document (`native.html`, zero Cicero) reproduces the same top/bottom asymmetry.** *Breaks* if `native.html` shows the override working correctly for both boxes, which would mean Cicero's own rendering introduces the asymmetry.
3. **Neutralizing the author's own `@page` margin-box `content` declarations in the live CSSOM, once `capture.js` has read what it needs, makes case 17 fully green in both render modes, with zero regression to cases 12/15/16 or the wider suite.** This is the structural fix either way predictions 1-2 resolve: it closes the whole class (a second chrome channel existing at all), not just this instance. *Breaks* if case 17 still fails after neutralization.
4. **The fix requires no change to `capture.js`, `driver.js`, or `chase.js`.** *Breaks* if implementing it turns out to require touching any of the three.
5. **No standing gate tally moves except case 17's own verdict.** *Breaks* on any change in `gates/records.js`.

## Verdict

**Prediction 1 held.** A live diagnostic, instrumented against the case's real document, read `<beltype-page>`'s own shadow-DOM cells directly (`el.shadowRoot.querySelector('[data-box="top-center"]').textContent`, matching the `dataset.box` attribute `chase.js` actually uses). On both title pages, both `top-center` and `bottom-center` cells were `''` — exactly matching `capture.js`'s own resolution. The shadow DOM, and everything that feeds it, was correct throughout. The bug was never inside it.

**Prediction 2 broke, cleanly — and the way it broke settles the diagnosis.** Chromium's own unmodified print of the case's document (`cases/runner.js`'s `native.html` path, zero Cicero involvement) showed no leak at all: both title pages' top and bottom bands empty, ordinary pages' top-center showing the base string exactly once. The asymmetry does not exist in raw CSS Paged Media as this document exercises it. This is not evidence of "no bug" — it is evidence of *where* the bug lives: entirely inside Cicero's own print-time DOM restructuring, not in any Chromium cascade quirk.

**This refines rather than simply falsifies the Context's leading theory.** The dichotomy this entry framed — "a genuine Chromium quirk" versus "something Cicero's code does wrong" — turned out to be a false one. What actually happens is a two-step interaction: Cicero's own `#pressSheet` renames every page to a synthetic geometry name so its `size`/`margin` win cleanly, which as a side effect strips every AUTHOR page-name selector (`title`, `interlude`) of anything left to match — and *that* is what hands the bare, unnamed base rule sole, unconditional native reach over every page's margin-box content, through Chromium's own perfectly ordinary cascade rules. Cicero introduces the *precondition*; Chromium's native engine supplies the *mechanism*. Neither half alone is "the bug" — read separately, capture.js's correctness and Chromium's own correctness on the raw document both looked like exonerations, and both were right, and neither was the whole story.

**Prediction 3 held.** `capture.js`'s `neutralizeMarginBoxes(doc)` — walking every `CSSPageRule` across `doc.styleSheets`, clearing `content` on each margin-at-rule child, touching nothing else — called once from `root.js`'s `present()`, right after `ensureDressingSheet`. `cases/runner.js 17` is fully green in both render modes. `cases/runner.js 12 15 16` (the family's other margin-box cases) and a full `cases/runner.js` run (all eighteen) show zero regression — "every case holds."

**Prediction 4 broke, and this entry's own Step 3 sketch already said it would.** The fix needed a small addition to `capture.js` (the new export) and a two-line call site in `root.js` — not a change to `driver.js` or `chase.js`, which stayed untouched as predicted, but `capture.js` itself was not immune the way the prediction claimed. Worth recording plainly rather than quietly editing the prediction after the fact: this was written before rereading `capture.js`'s own natural fit for the fix (it already owns `MARGIN_BOXES` and the CSSOM-walk pattern the new function reuses), and the prediction should have said "no change to `driver.js` or `chase.js`" — the two files actually confirmed clean by the readings this entry cites.

**Prediction 5 held.** `npm run gates` — the full battery, 25 gates including every differential range, every probe suite, and `cases` — reports 25/25 ok, "every standing record reproduced," pinned to `beltype@8e9d58c`. No tally moved anywhere.

**Too good to be true, checked.** Whether `@bottom-center` was truly immune to the native leak, or merely leaking a value numerically identical to the shadow DOM's own (`counter(page)` resolving to the same digit either way, making a genuine duplicate indistinguishable from a correct single value under a presence check) was never settled — the diagnostic confirmed the *bottom band's PDF text* was genuinely absent on the title pages (not just deduplicated by coincidence), which argues against pure numeric masking, but a full explanation of why the native cascade painted one box and not its sibling was not required to close this entry, since the fix removes the channel for both regardless of the exact mechanism. Recorded honestly as open rather than claimed as understood.

## Consequences

`packages/engine-cicero/src/capture.js` gains one new export, `neutralizeMarginBoxes(doc)`; `root.js`'s `present()` gains a two-line call to it, right after `ensureDressingSheet`. `driver.js` and `chase.js` are unchanged. `cases/17-the-borrowed-dress` moves from red-by-design to holding; its README and the checklist's frontier line are updated to close the finding rather than merely note it. `cases/16-the-shared-band`'s own README, which had pointed at 17 as "not sound everywhere," is corrected — the unsoundness was never in the cross-rule merge 16 and 17 share, only in a separate, now-closed channel outside it. Every other held case and the full `npm test` suite in `packages/essay` stay green. Two `pin.test.js` assertions were seen failing mid-session purely because `packages/engine-cicero/src/` was uncommitted at the time they ran (`cycle.md`'s own stated precondition: a pin cannot vouch for dirty engine source) — expected, not a regression, and resolved by this entry's own commit.
