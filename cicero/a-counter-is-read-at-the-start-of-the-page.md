# A counter is read at the start of the page

**Status: Decided 2026-09-14, Executed 2026-09-14.**

## Context

css-page-3 §6.1 carries one sentence that is the whole mechanism of a counter-driven running head: *"If a counter that has not been reset or incremented within the margin context or the page context is used by counter() or counters() in the margin context, then the resultant value is exactly as if the page-margin box were an element within the document at the start of the page, inside the deepest element in the normal flow that spans the page break."*

Nothing in this engine read it. `resolveContent` knew `page` and `pages` and no other name, so `content: "Chapter " counter(chapter)` printed the word and nothing after it. `cases/37-the-counter-at-the-start` was authored red against the sentence on 2026-09-14 — three pages, a heading that increments an ordinary counter, and a top box that should read `Chapter 0`, `Chapter 1`, `Chapter 2` because the sentence says *start* and the second page's heading sits sixty millimetres down. **Chromium has no opinion to borrow**: P33e measured it reading the counter as ZERO on every page, the document's increments never reaching the box, which the case records as the browser's own divergence and must keep recording.

The design open that convened this also named the build: *the state of the document's counters and strings at the entry's start position* is what a named string (`string-set`, GCPM) will need too, and it should be built once for both.

## Decision

**One module answering one question — what did the document's counters stand at, at this position — built in the driver while the source is still rendered, and carried in the account's `closes`.**

**One — `src/document-state.js`, and the name is the interface.** It answers *the state of the document at a position*, and counters are the first thing it holds; a named string is the second, and `string-set` will be a second op kind on the same log rather than a second walk. Its two halves split on the DOM: `counterOpsOf` walks the element tree once, in document order, reading `counter-reset`, `counter-increment` and `counter-set` off a `styleOf` it is handed; `counterStateAt(ops, pos)` replays them. The replay is pure, so CSS 2.1's *Nested counters and scope* is checkable without a browser.

**Two — the reading happens in `paginate`, not in `present`, and the measurement that settles it is sharper than the claim it was meant to confirm.** The standing finding said `getComputedStyle` *"returns an EMPTY declaration for an element in no flat tree — a detached node, or a block already moved into `<beltype-root>`'s light DOM and not yet assigned a slot"*. **Measured on `cases/37`, that is true of the detached node and NOT of the unassigned slottable.** An unassigned light child of a manual-assignment shadow host answers a full declaration — 474 properties, `display: block`, `counter-increment: chapter 1` — while a detached element answers 0 properties and empty strings for all of them. What the unassigned element gets wrong is **inheritance**: its `font-size` reads `16px`, the initial value, against `12.6667px` in the document, because it has no inheritance parent. So the class of failure is narrower and meaner than recorded — a non-inherited property survives the intake and an inherited one silently reverts to its initial value, which is exactly why the four properties the composition reads degrade in silence while the em it measured refused out loud.

That measurement would have permitted reading the counters at present time, since `counter-*` are not inherited. **It is still the wrong seat, for three reasons.** The driver already holds the cursor at the page's start position and the position index the walk needs, so the question is already asked there and nowhere else. The account is where a page's conditions live *by construction*, and the 2026-08-04 account ruling forbids deriving one fact twice. And the next reader on this module is a named string, whose content comes from `string-set` on **inherited** text — so a present-time seat would work today and break silently on the first thing built over it, which is the failure mode this round has just finished measuring.

**Three — a position is `bases[block] + wordsBefore(el)`, and an op applies when its position is STRICTLY BEFORE the page's start.** That is §6.1's *deepest element that spans the page break* said in this engine's own position space, and it is exact rather than approximate. An element whose first word IS the page's first word begins on the new page and does not span the break, so its own reset or increment is not yet in force — which is what makes case 37's second page read `Chapter 1` and not `Chapter 2`. An element that spans the break started before the page's first word, so it is included. The ancestors above the top-level blocks — `html` and `body` — are recorded at position **−1**, because they open before the document's first word and span every break there is; that one integer is what makes the first page's answer (`counter-reset: chapter` on `body`, already in force) fall out of the same comparison instead of needing a special case.

**Four — the page counters keep their path and take precedence, which is §6.1's own order.** `counter(page)` and `counter(pages)` are answered from the Ledger before the document's state is consulted at all. *"If a counter is reset or incremented within the page context, it is in scope for all page-margin boxes and obscures all counters of the same name within the document"* — the page counter is always incremented in the page context by definition, so it always obscures a document counter of the same name. A document that declares `counter-reset: page` on an element gets the folio, and that is the specification's answer rather than a shortcut.

**Refused: `counter-reset` and `counter-increment` in the page and margin contexts.** That is design open (2), and it is a design question rather than a repair: Chromium's page counter is a per-page function where CSS 2.1's counter carries a reset, §6.1 says page counters *"in all other respects"* behave as CSS 2.1's, and the front-matter restart idiom is exactly where the two readings part (P33b–d, g, h). A build here would take that decision by accident. Unchanged, and still held as `the-restarted-count` on chapter ten.

**The limits, stated rather than discovered.** The walk reads elements, so a counter operation on a `::before` or `::after` is not seen; `display: none` elements are skipped, which is CSS 2.1's own rule; a list item's implicit increment is not modelled; css-lists-3's `reversed()` counters are not modelled; and a top-level `position: fixed` box is not walked, because it is not among the flow blocks the position index is built over. Each is a real gap and each would show as a counter reading low.

**Refused: laws.** None moves. I4 again — chrome resolved from a Ledger read and delivered as a literal, with one more thing the Ledger's entry now carries.

## Predictions

Frozen on write.

1. **`cases/37-the-counter-at-the-start` goes green on both Cicero columns** — `Chapter 0`, `Chapter 1`, `Chapter 2` — and **Chromium's column stays declared divergent and stays actually divergent**, reading `Chapter 0` on all three. *Breaks* either way: a Cicero column reading `Chapter 0` three times would mean the position comparison is not strict; a Chromium column that stopped differing would mean the case or the browser had changed.
2. **The strictness of the comparison is what page two turns on.** If an op at a position equal to the page's start were included, page two would read `Chapter 2` — the heading that opens sixty millimetres down would be counted before its own page began. *Breaks* on `Chapter 2`.
3. **Every other case is unmoved**, 36 and 38 included. No case but 37 writes an author's counter in a margin box, and `counter(page)` is answered before the document's state is consulted. *Breaks* on any changed check.
4. **The DOM-free suite gains pins for CSS 2.1's scope rules over plain object trees** — a reset opening a scope that carries to following siblings, a nested reset shadowing an outer one, `counters()` reporting the whole nesting, an increment with no reset anywhere behaving as though the root had reset it, and the strictly-before rule at a page seam. *Breaks* if the walk cannot be exercised without a browser, which would mean the DOM half and the arithmetic half are not actually separable.
5. **No standing number moves.** The corpus's generated documents declare no margin boxes, so nothing resolves any content; the walk itself is additive work in `paginate` and decides no cut. *Breaks* if any gate's tally moves.

## Verdict

**Prediction 1 held on both halves.** `cases/37-the-counter-at-the-start` is green on `cicero` and `cicero-composed` — `Chapter 0`, `Chapter 1`, `Chapter 2` — and Chromium's column is still asserted divergent and still actually divergent, differing on exactly the two pages it differed on before: *page 2 top-center: 'Chapter 0' (want 'Chapter 1'); page 3 top-center: 'Chapter 0' (want 'Chapter 2')*. The browser generates the box, names the counter, and the document's increments never reach it, which is what P33e measured and what this case keeps on record.

**Prediction 2 held, and it is the prediction the build turned on.** Page two reads `Chapter 1`. Its own heading sits sixty millimetres down the page and is not counted, which is the strict comparison doing its work; an inclusive one would have printed `Chapter 2` there and `Chapter 3` on page three.

**Prediction 3 held.** Cases 12, 15, 16, 17, 20, 30, 31, 36 and 38 are unmoved check for check, and the run ends *every case holds* — the first run of this group with no failure in it since the three cases were authored.

**Prediction 4 held, and one of its pins was WRONG on first write, which is the pin working.** The suite goes from 121 tests to **133**: nine in a new `test/document-state.test.js` and three appended to `test/capture.test.js`, all over plain object trees with an injected `styleOf`. The test that failed claimed a reset's scope ends with the element that created it. **It does not**: CSS 2.1 gives the scope *"the element's descendants and the element's following siblings with their descendants"*, so a paragraph after the section that reset the counter is still inside the scope and the count continues — the implementation was right and the expectation was not. The pin now asserts both halves, the following sibling inside and a sibling of the section's PARENT outside, which is where the scope genuinely ends.

**Prediction 5 is answered by the battery, in the round's own changelog entry.**

**Too good to be true, checked — and the measurement that convened this fix came back sharper than the claim it was meant to confirm.** The standing note said `getComputedStyle` answers an empty declaration for a block moved into `<beltype-root>`'s light DOM and not yet slotted. Measured directly on `cases/37`: the unassigned slottable answers a **full** declaration — 474 properties, `display: block`, `counter-increment: chapter 1` — and only the DETACHED element answers 0 properties and empty strings. What the unassigned element gets wrong is inheritance, and only inheritance: its `font-size` reads `16px`, the initial value, against `12.6667px` in the document, and the three properties the composition reads do the same — an author's `text-align: justify`, `text-indent: 2em` and `hyphens: auto` read back as `start`, `0px` and `manual`. So the failure class is narrower and meaner than recorded — a non-inherited property survives the intake and an inherited one silently reverts to its initial value — which is exactly why the composition's four reads degrade in silence while the em it measures refused out loud. **That measurement would have permitted the present-time seat**; the driver was chosen anyway, and the third of the three reasons is the one that matters: a named string reads inherited text, so a seat that works for counters today would break silently on the first thing built over this module.

**One limit found while writing, not after.** The walk reads elements, so counter operations on `::before`/`::after`, a list item's implicit increment, css-lists-3's `reversed()` counters, and a top-level `position: fixed` box are not seen. `reversed()` is skipped by name rather than mis-read as a counter called `reversed(x)`, and that is pinned.
