# Page lengths are measured

**Status: Decided 2026-08-28, Executed 2026-08-28.**

## Context

The finding is recorded on [the checklist's](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/packages/engine-cicero/docs/css-paged-media-checklist.md) design opens, where it has been the capture slice's only geometry entry since [a page rule reads its own declarations](a-page-rule-reads-its-own-declarations.md) closed the one above it: [`src/capture.js`](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/packages/engine-cicero/src/capture.js)'s `toPx` ends `throw new Error('unsupported page length: …')` for anything outside `px|pt|in|cm|mm|q`, so a `rem`, an `em`, a `%`, a `calc()` or a `var()` in a page margin takes the whole render down rather than one measurement. It was latent while a page rule reads its own declarations's text-parsing fault was the only route into it — that fault dragged a margin box's own margin into the page-margin path, and margin boxes are exactly where relative units live (ZENTE's folio declares `font-size: .88rem`). The fix removed the route and did not make the function safe. `@page { margin: 2rem }` is legal CSS a web author writes without thinking, and it throws from inside the per-page loop — pages deep, after fonts and the measure context — which is the worst clock this engine has.

[two cases from a second stranger](two-cases-from-a-second-stranger.md) filed the finding to the dressed-page chapter's `wanted` list as `relative-page-margins` and said in as many words that the decision owed *"is a design round's, not this venue's"*, because the checklist frames it as a choice between two non-equivalent candidates: resolve relative units against the root's computed font size, or refuse them by name in I5's manner. This entry is that round's decision, and it is neither of those two.

## Decision

**A page length is resolved the way every other length in this engine is resolved: by asking the browser.**

The [tablet's](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/packages/engine-cicero/docs/design-tablet.md) founding stance is that *the browser is an oracle: it owns all geometry, we own all typographic decisions — one brain, no second engine, ever.* `PX_PER` and its regex are a second length engine — small, but a length engine, and it is the reason `2rem` is fatal: `rem` is not in its table, and the only reason `rem` is hard is that nothing had asked the browser. **This supersedes the checklist's binary framing** because both of the framed candidates concede the same premise, that Cicero must itself know what a length is worth. Resolving against the root font size is a hand-rolled `rem` implementation with `em`, `%`, `calc()`, `min()`, `clamp()` and every future length unit still outside it; refusing by name tells a web author that a subset of CSS is off-limits for a reason that amounts to our not having asked. The oracle already knows the answer, on a document that is live, with fonts awaited and the root's own cascade in force.

Seven parts, each with its reason.

1. **Absolute units keep the spec-ratio fast path.** `PX_PER`'s six ratios are the specification's own definitional constants (1in = 96px), not a second engine's opinion, and keeping them makes every existing document's numbers bit-identical — which protects the standing gate tallies and the composition-cache and `contentW` identity comparisons, where a number *is* a cache key. Only lengths the table cannot answer reach the probe. A fast path that changes no number is also what keeps this entry's verdict readable: one thing moves.

2. **The probe, and its `%` base is PER AXIS.** Modeled on [`src/measure.js`](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/packages/engine-cicero/src/measure.js)'s `createMeasureContext`, which is this house's precedent for measuring on a live document without disturbing it: an engine-owned, `__beltype`-prefixed wrapper, positioned `absolute; left: -100000px` and never `display: none` — display:none has no geometry — appended under `doc.body`, so the root's font size and the root's custom properties are inherited naturally rather than reconstructed. The raw declared value is seated as `margin-top` on an inner element — margins accept negatives and percentages, which `width` does not — and the browser's answer is read back through `getComputedStyle(...).marginTop`, whose resolved value for a laid-out box is the used value in px. **The wrapper's `width` is the percentage base, and which page dimension it carries depends on the side being resolved:** css-page-3 §6 states that percentages on the page context's margins are relative to the containing block's *width* for left and right values and to its *height* for top and bottom values — the page context deliberately differs from an ordinary element, where all four sides resolve against the inline size. So the wrapper is dressed `width: <pageW>px` when resolving a left or right length and `width: <pageH>px` when resolving a top or bottom one, still reading back through `margin-top` either way, because the probe's own inner element is an ordinary element and its `margin-top` percentage therefore takes the wrapper's inline size — which is exactly the lever that lets one mechanism serve both axes. The wrapper also carries the page context's font (the root's computed `font-size`; where an `@page` rule declares its own, that declared value is set on an inner element so relative chains resolve through inheritance — the browser does the resolving, not us). `topLevelBlocks` and the harness serializer already exclude `__beltype` ids by construction, so nothing downstream sees it, and it is disposed before `readGeometryTable` returns; C5 is honored the same way `createMeasureContext` honors it, by owning the element rather than writing the author's.

3. **Refusal moves to intake, by construction.** `readGeometryTable(doc)` is called from `driver.js` after `assertRenderConditions` and `await awaitFonts(doc)` and before the build loop, which is exactly where a refusal belongs and where the probe's preconditions are met. At the end of that function every reachable condition is swept — each declared page name plus the unnamed page, × `:first` × parity, a small finite set — so every resolvable length resolves at intake and every unresolvable one throws there, as a bare `Error` in `measure.js`'s intake style, naming the exact declaration: `unresolvable page length '<raw>' — …`. It surfaces through the seam's existing degrade path (console.error plus the unpaginated document) rather than as an uncaught throw mid-loop. `pageFor` stays synchronous and keeps its signature; the out-of-package callers (`packages/essay/lib/client.js`, `seeds/benchmark.js`) are untouched.

4. **The unresolvable residue, and its fallback stated in advance.** A `var()` that resolves to nothing is invalid at computed-value time and computes to `0` — indistinguishable from an honest `0` by a margin read alone, and an engine that lays out against a silent zero is the confetti finding by another road. The detector to be measured before any engine code is written (step 3 below) is a **registered custom property**: `CSS.registerProperty` with syntax `<length-percentage>`, `inherits: false`, and a distinctive `initialValue` sentinel, so an IACVT declaration falls back to the sentinel and failure becomes legible. **If the measurement holds, an unresolvable `var()` refuses by name. If it does not, the fallback rule is: a value containing `var(` that measures 0 refuses by name** — over-refusing an honest `var(--x)` that really is zero, which is a cost stated here rather than discovered later. Whichever branch the measurement selects is recorded below, and this paragraph is not rewritten to match it. Viewport units are a separate acceptance: on a screen-only beta they resolve against the window, and we take the browser's answer and say so — consistent with I5's relaxed-DPR preview posture, where a decision is valid for the screen being looked at and the console says which screen.

5. **Named refusals, a page rule reads its own declarations's discipline — one thing moves per battery run.** `driver.js`'s legacy `toPx`/`readPageGeometry` stays untouched: it is the judge-measure and benchmark reader, the corpus pins absolute geometry through it, and widening it here would move a second thing. The checklist's absurd-geometry intake refusal stays **owed**, not built: a content box of zero or less is a different question from an unreadable length, and this sweep does not acquire a geometry floor by accident. `marginBoxesOf`'s content-only condition is untouched, for the reason a page rule reads its own declarations gave when it refused the same widening.

6. **The eager sweep validates LENGTHS only — the no-size refusal stays on today's lazy clock.** `pageFor` throws `@page for '<name>' has no explicit size` for a condition whose cascade yields no `size`, and today that fires only for conditions the content actually reaches. Sweeping eagerly would move that refusal to intake for every *declared but unreached* named page, so a document that renders today would stop rendering — a second behavioral change smuggled into one round, and a strictly worse one, since it breaks documents that were never broken. The sweep therefore tolerates the no-size case and re-throws everything else. The residual asymmetry is deliberate and is the price of moving one thing: an unresolvable length is caught for every declared page, an absent `size` only for a page some content reaches.

7. **Memo and edge details.** The memo key is (raw string, **governing dimension in px**), not the raw string alone: per part 2 the governing dimension is `pageW` for left and right and `pageH` for top and bottom, and it differs per named page besides, so a key on the raw string alone would hand one page's `10%` to another page — or, worse, one axis's `10%` to the other axis on the same page. A `%` inside a `size` descriptor refuses by name — css-page-3 §7.1 gives `size` no percentage values at all, and `sizeToPx` runs before either page dimension exists, so there is nothing to resolve against even in principle; this is spec-consistent rather than a limitation. `margin: auto` on the page box refuses by name for the sibling reason: the probe would read `0px` off it, because a flow-root child's `auto` margin used value is zero, but on a page `auto` means UA-determined — measurement can produce a number here and the number would be a lie, which is the silent-zero road this entry exists to close. `pageFor` is a closure inside `readGeometryTable`, so a resolver created in that body reaches both `sizeToPx` and the margin conversion with no signature change anywhere.

### Measured before building (2026-08-28)

*Recorded after the four facts of step 3 were measured in headless Chromium — `Chrome/150.0.7871.24`, this repo's own pinned baseline, driven through `packages/browser-chromium`'s `launchBrowser`. The decision text above is unchanged by it, which is what part 4's stated fallback exists to make possible.* See the Verdict for how each measured fact stands against prediction 1.

The probe was the one decision 2 describes: a `__beltype`-prefixed wrapper at `left: -100000px`, `display: flow-root`, `width: 500px`, `font-size` set to the root's computed `20px`, appended under `body` of a document whose `:root` declares `--pm: 2.5rem` and `--side: 7mm`; the raw value seated as a margin on an inner child, read back through `getComputedStyle`.

- **(a) holds.** `2rem → 40px`, `2em → 40px`, `10% → 50px`, `calc(1in - 3mm) → 84.6614px` (96 − 11.3386, exact), `calc(2rem + 5%) → 65px`, `min(3rem, 40px) → 40px`, `clamp(10px, 5%, 30px) → 25px`, `2vw → 16px`, and the absolute units the fast path already owns agree with `PX_PER` to the digit (`20mm → 75.5906px`, `0.5in → 48px`). The resolved value is the used value, in px, on an off-viewport laid-out box, for every length form tried.
- **(a′), unlooked-for and useful.** A value the CSS parser rejects — `2foo`, `garbage`, `red` — never enters the declaration at all: `inner.style.marginTop` stays the empty string, and the computed read is a meaningless `0px`. So **the declaration's own acceptance is a free syntax gate** available before any measurement is trusted, and it is used in the built code: a value the parser refuses is refused by name rather than measured to zero.
- **(b) holds, all four sides.** `10%` on a 500px wrapper reads `50px` for `margin-top`, `margin-right`, `margin-bottom` and `margin-left` alike — the specification's rule that percentage margins resolve against the containing block's *inline* size on every side, confirmed rather than assumed, which is what makes `width: pageW` the correct and sufficient dressing.
- **(c) holds, in both halves.** An unresolvable `var(--nothing-declares-me)` is accepted as a declaration and computes to `0px` through a plain margin read, byte-identical to an honest `0px` — so the plain read genuinely cannot tell them apart, and a chained `var(--empty-chain)` whose own definition is unresolvable behaves the same. The registered-property sentinel distinguishes both: with `--__beltype-len` registered as `syntax: '<length-percentage>', inherits: false, initialValue: '-999983px'`, seating the raw value on the custom property and the margin on `var(--__beltype-len)` yields `40px`/`50px`/`84.6614px`/`0px` for resolvable values and exactly `-999983px` for `var(--nothing-declares-me)`, `var(--empty-chain)` and `2foo`. **Decision 4's primary branch is therefore the one built; the stated fallback rule is not needed and is not used.**
- **(d) holds.** A probe seated under `body` inherits the root's custom properties without being told to: `var(--pm)` reads `50px` (2.5 × the root's 20px, so the `rem` inside the substituted value resolves in the probe's own context too), `var(--side)` reads `26.4567px` (7mm, exact), and `var(--nothing-declares-me, 3rem)` correctly takes its fallback at `60px` rather than refusing — an author's declared fallback is a resolvable value and is treated as one.

**One residue named while measuring, and refused rather than measured:** `margin: auto` on an `@page` is a valid declaration that the probe would read as `0px`, because a flow-root child's `auto` margin used value *is* zero — but on a page it means "UA-determined", which is a different thing from zero and not something this probe is answering. It joins `%` inside a `size` descriptor as a refuse-by-name case: measurement can produce a number here, and the number would be a lie. No document in the corpus or the case family declares it (every existing `@page` margin in the venue is in `mm`), so nothing that renders today is affected.

**A fifth measurement the predictions did not name, and it is the one that changed the build.** Before committing the case, what Chromium's **own print** does with each margin form was read out of the printed PDF's ink position — the venue's ground truth is the printed page, and `getComputedStyle` cannot see a page context at all. A `320pt × 460pt` page, root `font-size: 10pt`, `:root { --outer: 12mm }`; the absolute control fixes the baseline-to-page-edge offset at ≈10.65pt and every other row is read against it:

| declared | ink x | top gap | resolves as |
| :--- | ---: | ---: | :--- |
| control `10mm / 12mm / 12mm / 15mm` | 42.75 | 39.00 | left 15mm = 42.52pt ✓ |
| `margin: 2rem` | 20.25 | 30.75 | 20pt on both axes — `rem` takes the root's 10pt |
| `margin: 2em` | 20.25 | 30.75 | identical to `rem` — the page context's font **is** the root's |
| `margin: calc(1in - 3mm)` | 63.75 | 74.25 | 63.50pt on both axes ✓ |
| `margin: var(--outer)` | 33.75 | 44.25 | 34.02pt on both axes ✓ — a root custom property reaches the page context |
| `margin: 10%` | 32.25 | 56.25 | left **32pt = 10% of the 320pt width**; top **≈45.6pt = 10% of the 460pt height** |

Four of the five forms are free: `rem`, `em`, `calc()` and `var()` resolve in Chromium's page context exactly as this probe resolves them, which is the Oracle posture confirmed where it matters most. **The `%` row is not free, and it is why decision 2 above reads "per axis".** The first execution of this entry dressed the probe `width: pageW` for every side and would have answered a top `10%` with 10% of the page *width* — shipping a fresh disagreement with the oracle inside the very entry whose argument is that the oracle already knows the answer. The specification was then read rather than the measurement legislated from, per this package's own method rule that *the oracle is evidence, not authority*: css-page-3 §6 says percentages resolve against the containing block's width for left/right and its height for top/bottom, so Chromium's per-axis behavior **is** the spec and fact (b)'s all-inline-size result is the ordinary-element rule, correctly measured and correctly not generalized. Decision 2's dressing sentence and decision 7's memo key were amended before any engine code was written; the predictions were not touched. **This enters the Verdict as unpredicted** — prediction 1 named four facts and this is a fifth, and the entry that would have been built without it is not the entry that was built.

## Predictions

Frozen on write, break-versus-hold decided in advance.

1. **The four probe facts hold as stated.** (a) `getComputedStyle().marginTop` returns used px for `rem`, `em`, `%` and `calc()` on a laid-out off-viewport probe; (b) a `%` resolves against the wrapper's width for all four margin sides; (c) an unresolvable `var()` reads as 0 through a plain margin, and the registered-property sentinel distinguishes it; (d) a probe seated under the root inherits the root's custom properties, so a resolvable `var(--x)` resolves. *Breaks* if any of the four measures otherwise — and (c) breaking is the one that changes the built code, since decision 4's fallback rule then governs.

2. **Case `18-relative-page-margins` goes red before the fix for the right reason and green after, in both modes, native partition identical.** The red must be a page error naming `unsupported page length` — not a wrong page count, not a missing band. *Breaks* if it goes red for any other reason (which would mean the case is pinning something else), if it stays red after the fix, or if Chromium and Cicero divide the words differently.

3. **No standing gate tally moves.** `gates/records.js` is untouched; the absolute fast path is bit-identical arithmetic, so every existing document's geometry is the same number it was, and the cases gate is a pass gate, so a new green case changes no number. *Breaks* on any change in `gates/records.js`, which is a finding to report and never a number to edit.

4. **Root `npm test` and engine `npm test` stay green, and the essay's out-of-package callers are unaffected.** `pageFor` keeps its signature and its synchrony, so `packages/essay/lib/client.js` and `seeds/benchmark.js` need no change; the engine's own suites are DOM-free and cannot see `capture.js` at all, so they will pass either way — which is itself the prediction, and the reason the whole proof is next door. *Breaks* if any unit verdict changes, which would mean something reached capture that was believed not to.

## Verdict

**Prediction 1 held, all four facts, and the honest report is that four was the wrong number.** (a), (b), (c) and (d) each measured exactly as frozen — the measured-before-building block above carries the figures, including the registered-property sentinel returning `-999983px` for an undefined `var()`, a chained-undefined `var()` and parser-rejected garbage alike, which settled decision 4 on its primary branch and left the stated fallback unused. But the prediction named four facts about *an off-viewport probe*, and the thing that decided how the probe had to be built was a fifth fact about *Chromium's own print* that no prediction reached for. See the unpredicted paragraph below; the prediction is scored held because each clause it made is true, not because it was the right set of clauses.

**Prediction 2 held, and the red was worth watching twice over.** `18-relative-page-margins` went red before the fix for exactly the named reason — `unsupported page length: 2rem`, out of `toPx` at `capture.js:13`, through `pageFor` at `:163`, `conditionsFor` at `driver.js:107` and `paginate` at `:151` — and green after: eight pages presented and printed in both modes, every page 320 × 460 pt, totality clean, and `native.partition: identical` against Chromium's own eight. The value named is `2rem` rather than a percentage because page one is a `:first` page, so `@page :first { margin-top: 2rem }` wins there and `margin-top` is the first margin converted; the document's other three relative forms never got the chance to fail. The red was re-run against the case's final bytes after its geometry changed, so what the README records is what the case as it ships actually did, not what an earlier draft of it did.

**Prediction 3 held.** `gates/records.js` is byte-for-byte unchanged after a complete 25-gate run: 163 agree on the native differential with the same 18 legal divergences and 7 theirs-illegal, every composed and v3/v4 gate, every view gate, every probe P1–P32, the cases gate, both suites. The only files the run rewrote are `gates/PIN.json` and `RESULTS.md`'s pin block, and the only thing that moved inside them is provenance — commit, branch, subject, source tree, date, duration. The absolute fast path was kept precisely so this prediction could be made, and it is the reason this entry's verdict is readable at all: every existing document's geometry is arithmetic that did not change.

**Prediction 4 held.** Root `npm test` 401/401, engine 45/45, essay 78/78, `npm run test:workspaces` green across every package. `pageFor` kept its signature and its synchrony, so `packages/essay/lib/client.js` and `seeds/benchmark.js` needed no change and got none. The engine's own suites passed identically before and after, exactly as the prediction said they would have to — they are DOM-free and `capture.js` needs a CSSOM, so the whole proof was next door.

**Unpredicted, and it changed the build: the page context resolves a percentage per axis, and an ordinary element does not.** Fact (b) was measured on a plain element and held — all four margin sides against the containing block's inline size. Decision 2 was then written to dress the probe `width: pageW` for every side, which is what fact (b) licenses and what would have been built had the case been authored on the strength of the four facts alone. Reading Chromium's own print before committing the case is what caught it: `10%` on a 320 × 460 pt page prints 32pt at the left and ≈45.6pt at the top. The specification was then read rather than legislated from — this package's own dearly-bought rule, *read the text before amending a law from a measurement; the oracle is evidence, not authority* — and css-page-3 §6 turned out to have settled it already: width for right and left, height for top and bottom. So fact (b) was correctly measured and would have been wrongly generalized, which is a different and more interesting failure than a bad measurement. Decision 2's dressing sentence and decision 7's memo key were amended before any engine code was written, the predictions were left frozen, and the case now carries `margin-top: 10%` and `margin-right: 10%` as the same three characters resolving to two different lengths — so the thing that was nearly built wrong is the thing the case fails loudest on.

**Unpredicted, and it belongs to the instrument rather than the engine: case 18's red is the first demonstration of `NEEDED-FIXES` §4.1.** That entry records `cases/runner.js`'s missing per-case `catch` as an explicitly *untested* reading — the margin box leak earns a case predicted it would fire on case 15 and it did not, because an absurd geometry makes the engine paginate confetti rather than throw. This case is the first thing in the venue's history to make the engine throw, and the runner did not report a failed case: it died, printing a Node stack trace where the case report belongs, with no check ever evaluated. The reading was right. It is recorded in the case's README and in §4.1, and deliberately not fixed here — a battery run that moves two things tells you about neither, which is the same discipline a page rule reads its own declarations used to refuse this very entry's fault.

**And it was partly too good to be true — found by exercising the refusals after the battery, and recorded here rather than quietly fixed.** The four refusal paths this entry built had nothing in the battery exercising them, so they were driven by hand once the gates were green. Two of the four turn out to be very nearly unreachable from author CSS, and one hole this entry claims to close is still open:

- **A `margin` shorthand containing `var()` never reaches capture at all.** Measured: `@page { margin: var(--outer) }` leaves `rule.style.getPropertyValue('margin-top')` an empty string while `getPropertyValue('margin')` returns `var(--outer)` — the CSS pending-substitution rule, since a shorthand carrying a variable cannot be serialized into longhands until it is substituted. [a page rule reads its own declarations](a-page-rule-reads-its-own-declarations.md) deliberately reads longhands only, so the margin reads as absent and defaults to `0px`. Chromium's own print honours the same declaration at 34.02pt (12mm), measured. **So `@page { margin: var(--outer) }` lays out against a silent zero — the precise failure mode this entry's Context calls "the confetti finding by another road".** It is *not* a regression: before this change the longhands were equally empty and `toPx('0px')` returned the same 0. But the entry's Decision reads as though every `var()` is now answered, and only a `var()` in a **longhand** is — which is what `cases/18-relative-page-margins` exercises (`margin-left: var(--outer)`, green and identical to Chromium) and therefore what it pins. A shorthand with `rem` or `calc()` expands normally and is genuinely fixed, which is why the finding's own acceptance criterion holds. Filed to the checklist's design opens as its own entry; the fix is a decision about meaning — whether capture reads a shorthand when the longhands are empty, reversing part of a page rule reads its own declarations for the one case where the CSSOM cannot do the expansion for us — and it is not smuggled into this round's close.
- **The parser-rejection syntax gate is defensive, not load-bearing.** Measured: an invalid declaration never enters the CSSOM at all — `margin-top: 2blorp` leaves the page rule carrying no margin declaration whatsoever, so capture sees `null` and defaults to `0px` long before the probe is consulted. The gate is real and correct where a value does reach it; nothing in author CSS reaches it.
- **The `%`-in-`size` refusal is likewise mostly unreachable, and the reachable neighbour over-refuses.** An invalid `size` is dropped by the parser the same way, so `size: 50% 300pt` surfaces as the no-size refusal rather than the named one. The one non-absolute `size` that *does* survive into the CSSOM is `size: var(--w) 300pt`, and this build refuses it by name even when `--w` is a perfectly resolvable `200pt` — because `sizeToPx` passes a null base to keep percentages out. That is an honest refusal at intake rather than a silent zero, and it is strictly better than the mid-render throw it replaces, but it is more restrictive than the specification requires. Filed with the entry above.

**Too good to be true, checked.** Four predictions held and no tally moved anywhere, which is the shape a change makes when it is inert. Three checks say it is not. *If the resolver were never reached*, case 18 would still throw `unsupported page length` — it does not, and it went from a runner-killing exception to eight pages agreeing with Chromium word for word. *If the fast path had drifted*, every existing case and seed would have moved, since all 25 gates' geometry is declared in `mm` and flows through `absoluteToPx` — none moved. *If the per-axis dressing were cosmetic*, case 18 would still pass with one base, so the discriminator was checked by hand before it was relied on: the top margin is 46pt and the right is 32pt, a 14pt difference on a 15pt line, which cannot leave a partition identical across eight pages. The unmoved tallies are evidence the fault was **narrow** — it lived entirely in lengths no existing document writes — and case 18 is the only thing in the battery that moved, which is what it was authored to be.

## Consequences

`src/capture.js` gains a per-document length resolver and an intake sweep, and `toPx` stops being a function that can end a render. The checklist's `toPx` design open closes in place, in the second channel a named page cannot close's pattern, naming the mechanism and the refusal residue and pointing at the case as the pin; the two bullets around it — the absurd-geometry open above and the GCPM `string()` retraction below, which carries `marginBoxesOf`'s content-only condition — are explicitly untouched, and stay owed. `.claude/NEEDED-FIXES.md`'s §1.2 moves to its "Already fixed in this line" foot section, which empties the entry its own fix order named next. The architecture's Furniture gains one sentence: the capture duty is a CSSOM walk **plus a measurement**, on the `line-height: normal` write-back's precedent — that organ already writes a computed value back into the document rather than deriving it, so measuring is not a new kind of act for the Furniture, only a second instance of one.

What this decision **does not** buy, said plainly so nobody reads it as bought: the engine still has no floor under an absurd geometry (a resolvable but ruinous length resolves cleanly and paginates confetti, exactly as before); a named page declared and never reached still refuses lazily rather than at intake; a margin box carrying presentation and no content is still invisible to capture; and `driver.js`'s legacy reader still speaks the six absolute units alone. Each is a live entry on the checklist's frontier and each stays there.

The venue gains one case in the dressed-page chapter, `18-relative-page-margins`, and the chapter's `wanted` list loses the entry that named this fault — the promotion `test/book.test.js` demands, in one edit, since a slug sitting in both registers or in neither fails that test.
