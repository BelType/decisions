# The run resumes from an entry

**Status: Decided 2026-10-08.** Egildo's three rulings on the survey of the same day, recorded with the survey's corrections folded in. The brief and its survey are [`../../rounds/cicero/the-run-resumes-from-an-entry.md`](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/.claude/rounds/cicero/the-run-resumes-from-an-entry.md); this entry is what a session builds from.

## Context

The editing tools recompile the document on every edit and reload the preview frame, because `run()` adopts the document destructively and is not re-entrant: measured on 2026-10-08, a second call on the manual reports one page and nests a second `<beltype-root>`, and on the essay book it overflows the stack. Every page is paginated again, every page is presented again, and the scroll position is lost. The feature wanted is the one the trade has had since InDesign and Word: an edit dirties the page it lands in, the run restarts there, and stops at the first page that ends where it ended before — recomposition to convergence.

**What the rivals do.** Vivliostyle stores a layout position per page start and, after laying any page, re-lays the following page only when its new start differs from the stored one (`epub.ts`, `maybeRelayoutFollowingPage`, `isSamePosition`). WeasyPrint stores one tuple per page start — the resume point, the next break and its side, the page's side, and the counter state — and re-makes the following page only when that tuple changed by value (`layout/page.py`, `remake_page`); it converges inside one render, in at most eight passes, and keeps nothing across renders. fragmentainers resumes from a stored fragment and always runs to the end. Blink's LayoutNG, read in the pinned build's source, is NOT this: its layout-result cache is indexed by the fragment's slot and guarded by dirty bits and constraint-space equality, and nothing in it compares an incoming break token to the one a cached fragment was laid from. The canon for this decision is WeasyPrint and Vivliostyle.

**What the survey measured, on which this rests.** Two runs over one document give byte-equal Ledgers in both modes, on the manual, the book and five cases — every field, every key order — within one realm and one viewport; the book paginates to 173 pages at a 1000 px viewport and 170 at 1400 px, because its own stylesheet carries a width media query the browser decides against the screen. After one word was appended to a paragraph on page 28 of the manual, no entry moved, but the flat projection `pos` shifted on 244 later pages; fifteen words moved pages 28 to 31; four hundred words on page 123 added a page, after which every later address equals the old ledger's one page earlier while page number and parity differ on all of them. The build loop carries one thing between pages that the entry does not hold and a cut reads: the parity a forced `left`/`right` break still owes. Named strings, running elements and counters reach no cut; they are chrome. The delivered `target-counter()` values are a document-level sheet fixed for the whole run and act as CSS. The clone per pour is already cheap (0.8 ms a page on the manual); what a restart cannot shrink today is `present()`, which rebuilds every page each run, 31 to 38 % of a default run, and in the composed mode the composition, which runs whole up front (3.6 s on the manual) with a cache keyed by the source element OBJECT, so a recompile misses on every paragraph.

## Decision

**One. The key is the address, under the run's conditions.** A page's cut is a pure function of its resume state, the content after it and the conditions it was measured under; the Ledger's entry is that state, read as follows. IN the key: every live flow's address — the place in the tree, the word, the character, the pixel extent of a divided word, the remainder a parallel flow or row item carries — the cut's class, whether the page began at a forced break, and **the parity a forcing ahead still owes, which the entry now carries** rather than a loop local, because a key that must be helped by an index is not a key. OUT of the key: the flat projection `pos`, the page number, the presentation literals, the trace's measured `y`, and the parity, except where a parity can change a cut — a geometry that differs between left and right pages, or an owed parity — in which case it is in. The run's conditions are part of the key and are compared once per run, not per entry: the stylesheets' text after the seam's rewrite, the delivered read values, and the measuring realm's media environment — viewport, device pixel ratio, colour scheme — which is *a break decision is valid only under render-identical conditions* applied to the memo. A change to any of them dirties page one.

**Two. Convergence is equality of addresses under the page shift.** An edit dirties the page whose interval holds it, located by the belt's spine diff — the first node whose path, stamp or text differs from the previous build. The run restarts at that page with the Ledger truncated before it, the live `box` pointers resolved again from the addresses (C6), the owed parity read from the entry, the run-level indexes rebuilt over the new tree. After each page it compares the new closing entry's key with the old entry at the same page, or at the page shifted by the pages the run has added or removed, and stops at the first equality; every later entry is kept, re-indexed by the shift. The chrome — counters, named strings, running elements, folios, the contents page — is read again from the converged ledger, and the settle loop over the reads runs as it runs over a fresh ledger; a read whose delivered value changed is a changed condition and dirties the page holding its footprint, which the reservation already bounds.

**Three. The composition cache is keyed by the node's path and its text, not its object.** A recompile hands the engine a new tree; a paragraph whose path in the node map and whose text are what they were composes to the same lines at the same width, so the cache key is path, text and measure width, and the element object is no longer identity. A composed restart then re-composes only the paragraphs the edit touched.

**Four. The presentation replaces only the pages whose entries moved.** `present()` keeps the DOM of a page whose entry's key is unchanged, shifted by the page shift where one occurred, and refills only the dirty run. The Chase carries containment — `contain: layout size paint`, and `content-visibility: auto` with its intrinsic size set to the page size — so refilling one page cannot dirty the next and pages far from the viewport are neither laid out nor painted. The address at the viewport's top is the scroll anchor: a viewport above the edit keeps its pixel offset, a viewport holding the edit anchors to the word under the caret, a viewport past the converged run shifts by the page shift times the page pitch.

**The order of the builds, each a round of its own, each a Sonnet with this record.**

1. **The measure runs again on a presented document.** The intake hands the run the lists it took — blocks, fixed boxes, running elements — instead of the run re-reading `document.body.children`; the geometry table is captured before the margin boxes are neutralized; the dressing sheet's break neutralization reaches the presented fragments and not the sources. Proof: a second `paginate` over a presented frame returns a Ledger byte-equal to the first, in both modes.
2. **The run restarts at a page and converges.** The entry gains the owed parity; `paginate` takes a starting page and a prior ledger; the comparison above; the presentation per page with containment. Proof: the edit table below.
3. **The composition re-keyed.** Proof: a one-paragraph edit on the manual re-composes one paragraph.
4. **The editing tools stop reloading the frame on a document edit.** The spine diff, the scroll anchor, the three viewport cases. Their own DESIGN.md gets the entry; this record only names the seam the engine offers.

## Consequences

**Predictions, frozen on write.**

- Build one: a second `paginate` over the presented manual returns the same bytes as the first, default and composed; the page count is the fresh run's; every battery record reproduces, since a fresh run is the resumable run started at page one and nothing in the measure changes.
- Build two, on the manual in the default mode, repeating the survey's edits: one word appended on page 28 restarts at 28 and stops at 29, no entry moved; fifteen words on page 28 re-cut pages 28 to 31 and stop at 32; four hundred words on page 123 add one page, converge by the second page after the edit, and every later page keeps its DOM with its folio re-read. The whole of such an edit, measure and presentation and reads, finishes under half a second on the surveyed machine. No battery record moves.
- Build three: after a one-paragraph edit the composed run re-composes one paragraph, and the composition phase on the manual falls from 3.6 s to under 100 ms; the composed Ledger is byte-equal to a cold run's.
- Build four: the preview frame is not reloaded on a document edit; the scroll anchor holds in the three cases; a stylesheet edit that reaches the measure still dirties page one, by rule.

**What this is not.** Not incremental composition inside a paragraph; not a diff smarter than the first changed node; not Paged.js. A change to the run's conditions — a sheet, a font, the viewport, a delivered read — restarts from page one, and that is correct, not a limit to close.

**What it touches on the tablet: nothing.** Flow stays forward, since a restart is forward from the dirty page; the key's conditions are the render-identical law restated for a memo; the chrome stays resolved and never flowed. The architecture's build-loop section is redrawn by build two, and the seam's filed finding on re-entrancy closes with build one.

**Amended 2026-10-12 — a cut inside the box an edit replaced is an address into a tree that is not there.** Found by measurement on a thirty-two page book in the editing tools, by an insertion scan, and present on `main`: a paragraph inserted right after a chapter's header gave a resumed book of 34 pages with the chapter opening on a verso, against the whole run's 32 — silently, `road` patch and `why` null — and a paragraph of 225 words or more threw *the walk failed to advance at [4,2,1] word 17*, which the tab answered with a frame reload and so hid. The two are one fault. (1) **The cause.** An edit that changes how many children a top-level box has makes that box the edited one (the lowest box holding every difference IS the chapter), and `addressOf` names its start. `holderPage` asked `cutAfter(entry.cut, address, posOfCut)` of every prior entry, and `posOfCut` reads the NEW tree: the prior entry of the chapter's first page ended at `[4,2,1]` word 17, an address into the old section, which in the tree with the inserted paragraph names the second child of an ordinary paragraph — nothing. A cut that names no box projects to its block's start, which ties with the edit's address, and a tie is not *after*. So the page that ended inside the chapter was passed over, the next was taken as the holder, and the run restarted one page late with a kept page whose closing address named nothing; the cursor it resumed from was that nowhere, the chapter's text began a page late, a `break-before: right` that was owed no blank page got one and the other way about, and the run converged ten pages on, because from there the keys were the prior run's and every address lay clear of the edit. The long paragraph threw for the same reason: the cursor `[4,2,1]` word 17 was inside a paragraph that had become 225 words long. (2) **Why convergence accepted it.** Convergence compares the entry just written with a prior one under the page shift and asks that the addresses lie clear of the edit (`clearOfEdit`); both were true, because everything after the edited box IS the same. What convergence cannot know is whether the pages BEFORE it, the ones the run kept and the cursor it began from, were a lawful starting point, and nothing asked. The record's key says an equal address means an equal page; the clause it did not state is that a KEPT page's closing address must name a place in the document that is there. (3) **The fix, two pieces.** `holderPage` takes a cut inside the edited box (the edit's path a proper prefix of the cut's, the edit at the box's own start) as past the box's start before it asks the new tree anything, which is true whatever the box now holds; and the driver refuses to resume from a kept page whose closing cut names no box (`namesNoPlace`, `resume.js`), cutting the run whole and saying why (`the page the run would resume from ends at a place the document no longer has`). The second is a net under the first: no honest address reaches it now, a host naming the wrong box does. Cost, stated: a chapter that gains a child restarts at the chapter's first page, as the address says, where a smaller address (the first word that differs) would restart later; `patch.js`' unit of an edit is the box, and a finer address is a host question this record does not take. **Pinned** by `packages/essay/test/resume-inside-the-replaced-box.test.js` (red first: five words, sixty, 150 and 300 words inserted after the header, and a box at every child of the chapter at three sizes, resumed equal to whole in both modes) and `test/resume.test.js` here. **The case that was owed and is not one:** the document is printed correctly by a whole run and the question lives in the second call on a live frame, so it is an implementation pin on METHOD.md's line, not a case in `cases/`.


**Amended 2026-10-15 — every box replaced since the prior run is an edited box, not only the one the run resumes at.** Found by the studio experiment ([beltype#48](https://github.com/egildo/beltype/issues/48)): select the whole document, make every paragraph a bullet list, then an ordered one, then paragraphs again. The third resume threw *entry position runs backward (I1: flow is forward)* from `Ledger.append` ← `keepAfterConvergence`, and the pages stayed at the previous cut. (1) **The cause.** A select-all edit reaches the top level, so the studio patches every top-level box that differs and then calls `run({ resumeAt })` once per patched address, earliest first. The rim and the editing tools patch one box and resume before patching the next. The first of the studio's runs was told about its own box only. It restarted there, cut forward, and found an equal key at the first page that began at a later section's start. That address means the same in both trees, and `clearOfEdit` judged it clear because it lay past the one box the run knew about. So the run converged and kept the prior pages after it, and those pages were cut at addresses into the ordered lists the later patches had already dissolved: `[s,1,k]` word *w*, item *k* of the list. In the new tree, `[s,1]` is a paragraph. Its *k*-th child is an `<em>` when the paragraph has enough of them, and otherwise nothing at all, which projects to the section's start. One such cut projected before the page kept ahead of it, and the Ledger refused it. When the projection happened to run forward, the run kept pages cut from text that is no longer there and said nothing. The first two steps passed for that reason, by luck. (2) **What the record did not state.** Its convergence clause says an equal address is believed only past *the* edited box. Nothing in the engine said there was one, and `patch` returns an address without promising the host will resume before patching again. The editing tools' own comment called the one-box rule a host obligation; the studio read the seam's documentation and broke it in good faith. (3) **The fix.** The seam remembers every address `patch` answered since the run that left `previous` (`edited` in `seam/client.js`, taken off the list when a run leaves a new `previous`, and left in place by a run that throws). It hands them to the driver as `edited` beside `dirtyAt`. The driver restarts before the earliest of them all and converges only past the last: `clearOfEdit` and `converge` take the list of edited paths, and an address is clear when the main flow has left every edited box behind it and no carried flow stands inside or above any of them. The studio's later runs, one per box, then find nothing new to cut and converge at once. A host's choice of the place to resume at no longer decides whether the result is right; it only decides where the work starts. Cost, stated: a run that knows of a later edited box cuts every page up to it before it may stop, which is the work the per-box runs would have done anyway.
