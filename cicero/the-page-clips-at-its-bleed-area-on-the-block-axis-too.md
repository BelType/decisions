# The page clips at its bleed area on the block axis too

**Status: Decided 2026-10-02, Executed 2026-10-02.** Egildo's ruling, 2026-10-02, on the published text and not on any engine: **the page rendering clips at its bleed area only; document ink that stands above the page area's block-start edge paints in the page's top margin, under the page-margin boxes; the clip at the foot is not a page-area clip at all, it is the cut, and it stays exactly as it is.** The sibling of [*the page rendering clips at the bleed area*](the-page-rendering-clips-at-the-bleed-area.md), which did the inline axis on 2026-09-18 and named this half as its part (c); it closes the question [*the margin after a forced break is preserved*](the-margin-after-a-forced-break-is-preserved.md) left open on purpose. The case is [`cases/78-the-band-above-the-page-area`](https://github.com/egildo/beltype/blob/42b348b547d269a217a7f193042fe216386a4650/packages/essay/cases/78-the-band-above-the-page-area/README.md), authored red in both modes the same day.

## Context

A band pulled into the page's top margin by a negative `margin-top` and a `border-top` as tall (the print idiom a real venue writes for a title) was laid out exactly, 30 px above the page area, and painted on no page. The case measured why on the live page by lifting declarations and printing: `.content-area`'s `overflow-y: clip` in the Chase's shadow sheet and the flow's own `overflow-y: clip`, set by `setFlow`, each hide the band alone, and lifting both prints it at exactly the claimed rectangle in both modes. Both boxes begin at the page area's top edge, so each clips the same line; the host's clip at the page box does not reach a band that stands inside the margin.

**The two edges of the block axis are different edges, and the earlier record's part (c) joined them.** The FOOT of the flow is the cut: a continuation is a clone of the whole box with the consumed words blanked, and a first fragment is built with the words after its cut removed from the tree, so what lies below the cut is either not in the tree or is, and the clip is what keeps it off the page ([*the ink stops at the fragmentainer*](the-ink-stops-at-the-fragmentainer.md) priced widening it, [*the first fragment is constructed*](the-first-fragment-is-constructed.md) widened it where the tail was gone). The HEAD has no cut behind it. What a page holds above its area's top edge is either ink the document's own box put there, which is this round's, or ink that belongs to the page before, which a different clip hides (the slice wrapper's, below) and which this round does not touch.

## What the text says

The same four sentences the earlier record read, turned ninety degrees, and the case README quotes them against the snapshots in `packages/essay/book/spec/`: css-page-3 `bleed` names the page rendering's one clip and it is at the bleed area, which computes to zero without crop marks, so the page box, margins included; §3.2 recommends *"Content should be allowed slightly beyond the page box"* and leaves undefined only boxes *outside* it, which a band in the margin is not; §3.1's painting order, document contents and then page-margin boxes *"in front of"* them, is a rule about two things that can share a place, and only the margin is such a place; css-break-3 §5.2 preserves the margin after a forced break, a negative one included, so the band is the forced box's own ink. And CSS 2.1 §9.6.1, the one page-area clip any of these documents names, is stated for fixed boxes alone, and the furniture layer keeps it on both axes. css-page-3 is a Working Draft: this is a reading of published text and not a Recommendation's authority.

## Decision

**The flow keeps `overflow-y: clip` and its head edge moves to above the page box; the content area stops clipping.** Two changes, both in `src/chase.js`.

- **`setFlow`** gives the flow a block-start padding of one page's height and a margin-top of `-(lead + page height)` where it used to write `-lead`. A clip's edge is the PADDING box, so the padding is the head the clip gets, and the equal negative margin leaves the flow's content box exactly where it stood: the first box's border top still lands at the area's top less the leading margin the measure pass truncated, and the foot, `lead + used + ext + cost` below the content top, is the same sum as ever (the flow is `box-sizing: content-box`, so the `height` is the content height as before). The host's own `overflow: clip` at the page box is then the only clip the head meets. The padding is the page's height because that is more than the distance from the flow's head to the page box's top edge on every page by construction (the page area stands inside the page); it is not computed from the margin and the page's own border and padding because the exact figure would need the content area's resolved border and padding, which the account does not carry and which the host's clip makes unnecessary. `applyConditions` writes the page height beside the band width it already keeps.
- **`.content-area`** loses `overflow-x: visible; overflow-y: clip` and keeps `position: relative` (the furniture layer is absolute against it). What its block clip still hid, once the flow clips its own foot, was measured and is nothing: over every page of the 78 case documents in both modes no flow ends past the content area's foot by more than 0.03 px (rounding; 108 page readings, none above that), and the root passes every page a `usedPx`, so there is no page without a foot clip.

**Refused: `clip-path: inset(-N px … 0 …)` on the flow.** Measured on the live page by setting it in place of the padding: it paints both bands and the margin box over them, in both modes, so it works. It is not taken because it makes the flow a stacking context (`clip-path` does), which changes how an author's own positioned, `z-index`ed content interleaves with the margin cells and the fixed clones, and nothing in this round wants that changed; and because Caster reads the flow's border box as the page's clip, so a `clip-path` that leaves that box at the area's top leaves the printer dropping text above the area that the engine now paints. The padding moves that box with the clip. **Refused: `overflow-clip-margin`**, as [*the clip is a block-axis fact*](the-clip-is-a-block-axis-fact.md) refused it: uniform on both edges, so it would move the foot with the head.

**Left as it is: the slice wrapper's clip** (`fragments.js`, `overflow-y: clip` with a negative top margin). It is a third clip with a different job: it hides what the page before already showed of a divided painted box, which is ink that belongs to the previous page, and lifting it would paint that ink again. It is not at the head of the flow and this round does not reach it; case 04's plate and case 55's monolith, which stand 657 px and 260 px above their pages' areas inside a slice, were looked at on the live pages (below) and the margins above their areas are white.

## What the rivals do

Read for the one narrow question: does it clip document content at the page area's block-start edge.

- **WeasyPrint 70.0** (`weasyprint/draw/__init__.py`, `draw_stacking_context`) clips a box only `if box.style['overflow'] != 'visible' and not isinstance(box, boxes.PageBox)`, with the comment *"Dont clip the page box, see #35"*. The case README ran it: both bands at 22.5, 0, 105 × 22.5 pt on the pages that own them. **Taken**: the page box is not clipped at its area.
- **Paged.js classic** (`src/polisher/base.js`). The clips are `.pagedjs_sheet { overflow: hidden }` (the sheet, the page box plus its bleed), `.pagedjs_bleed` and the footnote area's; the content element carries none. Run through `beltype build --pdf` by the case: both bands where the text says. **Taken**, and it is the same arrangement as this decision's, the sheet being the clip.
- **pagedNG** (`src/components/PagedPage/PagedPage.js`) clips `.page` and `.sheet`, both the page box; nothing at the area. Read, not run. **Taken**.
- **fragmentainers** (`package/src/components/fragment-container.js`) clips its host with `overflow: clip` at its own box, and models no page margins, so its fragmentainer is the nearest thing to a page area and a band above it would be clipped. **Not taken**: it is a library whose container has no margin to hold the ink, not a ruling on pages.
- **Chromium's own print** clips at the page area and sends the forced page's band to the foot of the page before (22.5, 180 pt on case 78's geometry), where the text sends nothing back. It stays a declared paint divergence on case 78, asserted to differ so the day it stops differing somebody re-reads the declaration.

## The audit

Every item is marked measured or read.

1. **What stands above a page area's head on any page, and was hidden only by this clip.** Measured by a scratch survey over all 79 case documents, both modes, listing every element in the flow whose box begins more than half a pixel above its page area's top. It found: the two bands of case 78; the band of case 77's forced box (page six, the same shape, now painted in the margin: the case claims it is NOT inside the page area, and still holds); case 45's rotated continuation, whose own rotated corner swings 4.78 px above the area (its own ink, §5.5's per-fragment origin, and the case holds); and the plates and monoliths inside a slice wrapper in cases 04 and 55 (above by 657 px, 1315 px and 260 px), which the wrapper's own clip hides, confirmed on the live pages' screenshots, where the margin above the area is white. **Nothing of a previous page appeared** at any point of the work, on screen or in the print order, including transiently. On seven scratch documents of the shapes the brief names (a divided painted box with borders and a ground, a divided table with a repeating head and borders, a divided list, a float carried across two cuts, a monolith taller than three pages, a first-child chain of negative margins, and relative and transformed boxes), in both modes: no element stood above any area's head except where the document itself put it. The negative-margin chain's band is painted on page one only, its continuation on page two beginning at the area's top (a continuation's own leading decoration is zeroed, and nothing of it stands above). The relative and transformed boxes put their continuation's first lines above the page box by their own offsets (90 px against a 30 px margin), which the host's clip hides exactly as the old one did, and which is the document's choice; no word was lost to this round that was not lost before. The `leadPx` shift is the leading margin the measure pass truncated, so the pixels it moves are that margin's, which holds no ink (read in `root.js` and `driver.js`; the survey found no box above any area but those named). A page with `usedPx == null` does not exist: `root.js` passes every page its account's `usedPx`, blank pages included (read), and `setFlow` called without one gets no foot clip, which no caller does.
2. **Painting order with the margin boxes.** Measured on a scratch copy of the case with a green background on `@top-center`: on screen, the pixel at the middle of the overlap is green in both modes, and in the print the operator order on page one is the page ground, the band's `#0000c0`, then the margin box's `#00c000`, which is the cell in front of the band. `.band, .margin-cell { position: relative; z-index: 1 }` does what its note said, and the padding approach adds no stacking context, so it is not disturbed. **It stays wanted and not cased**: the runner's `paint` claim compares rectangles with their clip and carries no order, so it cannot say which of two overlapping fills is on top, and nothing here weakens or fakes a claim to look as though it could. A band taller than the margin, measured likewise (a 60 px border against a 30 px margin), prints as 22.5 pt at 0: the host's clip at the page box, which is the rule.
3. **Fixed boxes keep the page-area clip on both axes** (§9.6.1). Measured: the furniture clones' rectangles against their own page area, before and after, identical on every page: `7.55, 7.55, 226.77 × 22.67` on all three of case 24, `264.53, 0, 113.38 × 529.13` on both of case 32, `99.97, 0, 40 × 20` on both of case 46; and those three cases hold. The layer is still `position: absolute; inset: 0` against a content area that is still positioned, and its own `overflow: clip` was never the content area's.
4. **Caster** (`packages/caster/src/index.js`, `clipToPage`, and `adapters/cicero.js`): **read, not run, and not changed.** Caster clips text and drawings at `.flow`'s border box, `{ topPx, bottomPx }` page-local (S22). Its `bottomPx` is the foot and has not moved (measured: the flow's bottom is identical on every page of fifteen cases in both modes, old source against new). Its `topPx` moves up by one page height with the flow's padding, so Caster no longer drops a line standing above the area, which is what the engine now paints (a band's text used to be dropped by the printer and is not now), and it also no longer drops a line above the page box's top edge, which the engine hides under the host's clip and Caster would emit off the page (inferred from the code, not measured: there is no Cicero-to-Caster fixture here with text above the page box). That is the one disagreement and it is narrow; it is filed in `.claude/NEEDED-FIXES.md` with Caster's `DESIGN.md` as its owner (the clip should be the page box, not the flow's border box). `conservation.js` reads the same rectangle and so now counts words in that region as rendered.
5. **The measure feed is untouched.** Presentation only: nothing in the Gauge, the Stonehand, the driver or the positions was edited, and the pages' accounts are identical (the cases' partitions did not move: see below).

## Consequences

- **Wanted and not cased: the margin boxes in front of the band.** Measured once on a scratch document, as above; the runner cannot say it.
- **A continuation fragment's own head, where css-break-3 §5.1's *"must not be positioned above the block-start edge of the fragmentainer"* binds.** Not cased and not touched: a document with a first-child chain pulled above a continuation is not drawn by any case, and the survey above found no continuation whose ink stood above the area but a rotated corner and the author's own relative offsets.
- **`bleed` is still unmodelled**, so the limit is the page box; `overflow-clip-margin` is still the door when it is modelled, and it widens a clip uniformly, which is correct for `bleed` and is why it was refused here for the foot.
- **Caster's `topPx`**, above. Closed on Caster's side on 2026-10-03, and it had not been an inference: Caster's own suite was red from this round on, and its head is the page box now with the foot still the cut (`packages/caster/DESIGN.md` S69).
- **The tablet** is not touched. If a law there now reads false it is a design round's to say; none was found to quote.
