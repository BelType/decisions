# The render reads through the session

**Status: Decided 2026-09-24, Executed 2026-09-24; amended the same day to cover the editing tools and again when the closure got a pass of its own.** The second amendment is where core's read-set went ([below](#the-closure-reads-through-its-own-pass-and-the-read-set-goes)). Follows [Provenance watches the files](provenance-watches-the-files.md), and closes the regression that record accepted — in the CLI first, then in the editing tools ([below](#the-editing-tools), and `packages/editing-tools/DESIGN.md` 53).

## Context

The change feed (`packages/cli/src/change-feed.js`) held one Provenance session and was handed a whole watch set after every build. In the CLI that set was bookkeeping BelType kept beside the render: the target, the pipeline's `readSet` (the last good render's and the failing one's), every closure source, the cascade's config files, and `venueCandidates()`, the two places the venue probe looks. A read that failed was in none of those lists, so creating the chapter behind a broken `@include` rebuilt nothing — accepted as a regression when the directory watch went.

`@egildo/provenance@0.2.0` added read passes. `session.read(label)` returns a pass whose `host` has Cascata's shape and records every read with the SHA-256 of the bytes it handed out, and every location it found nothing at (a refused read, a `canonicalize` answering `undefined`); `pass.note(location)` records code read outside it; `pass.end()` makes all of those the label's roots, replacing the previous pass's with that label, settles once, and returns the manifest. A root in state `refused` is watched, and a file appearing there is a `changed`. A file rewritten between the render reading it and `end()` is a `changed` too.

## Decision

**Every dev-server read goes through a pass.** `start()` opens the feed's session on the target before `boot()`, so the first build is a pass like every later one. `build --pdf` opens no feed and reads with the plain node host.

**Two labels, because two things read.** *(Three since the amendment below: `closure` beside `render`.)* `render` wraps each `pipeline.build`; `cascade` wraps each `loadCascade` — the venue probe and the one `resolveConfig` in `boot()` and `reloadConfig()`, which run outside the pipeline. Each is ended in a `finally`, so a refused cascade and a failed render still leave their reads and misses watched: the broken file is exactly the one whose next edit must be heard. A render pass ends after `isBuilding` clears, because the change its `end()` may report must not be turned away as a build in progress.

**The host is stable and forwards.** `Pipeline` takes its host once, at construction, and a pass lives for one render, so `readThrough(base, documents, pass)` in `change-feed.js` builds a host once that asks `pass()` on every call. `read` and `canonicalize` go through the pass, and so does the real file under `<file>#frontmatter.yaml`, since core's `readText` strips the fragment before it asks. The virtual `--set` documents are served by the node host before the pass is asked, so a location that is not a file never becomes a root. `locate` and `paths` stay the node host's — `paths` deliberately, so a dev server and a `build --pdf` run read with the same platform facts. `loadModule` stays the node host's and `note()`s the location it returns. The orchestrator holds two such hosts, one per label, because the two passes can overlap: a config change arriving mid-render starts a cascade load, and each pass must record only its own reads.

**What is watched comes from the passes.** The explicit watching of the read-set, the config files and `venueCandidates()` is deleted from the CLI; the passes' roots cover all three, the probe's misses included. The feed still adds by hand, with `addRoot` and `removeRoot`, what no read covers: the closure's on-disk sources, which the page reaches for (a font, an image) and the render never opened. A stylesheet the closure scanned is both a pass read and a hand-added root, which is one source, reported once. *(Since the amendment below, the hand-added set is only what no read opens — binary and `beside` entries — and the scanned stylesheet is a `closure` read.)* Only `changed` is reported, as before.

**A change is classified by the cascade pass.** A batch naming any location the latest `cascade` pass read or found nothing at reloads the cascade; anything else rebuilds, once either way. **The document itself is left out**: the cascade reads the target, because its frontmatter is the cascade's entry, but every render re-runs the cascade over it, so a document edit rebuilds and never re-probes — as it did when the classifier was a list of config files with the frontmatter location dropped. A path is matched both as it arrived and as Provenance keys it (a realpath), because a created file arrives under the key its miss was recorded with, and a hand-spelled `/var/…` only matches a `/private/var/…` read once canonicalized.

## The editing tools

The editing server serves every read the tab's render makes, so it reads through the same feed, on one label: **the pass runs on the server, and the tab marks where each render begins and ends.**

- **A render opens a pass and names it on every read.** `rebuild()` posts `/_beltype/edit/pass` (token-guarded), the server calls the feed's `read('render')` and answers a random id, and the tab's HTTP host sends that id as `x-beltype-pass` on every read — `file`, which is also its `canonicalize`, and `module`. The host takes the id from a getter the app sets, as it takes `readDraft` and `homedir`, so it stays a pure host.
- **The server serves a tagged read through the pass's host**, after its containment guard, so the bytes the tab receives are the bytes recorded, and a read that finds nothing is a recorded miss. A module it resolves and can serve is `note()`d. A read with no tag or a stale one — the editor opening a file, the reconciliation after a `changed`, the picker — is served from disk and recorded nowhere.
- **Drafts are reported, then read from disk.** A read the tab's draft answers never reaches the server, so the tab collects those locations during the render and sends them as `drafts` when the pass ends; the server reads each one inside a readable root THROUGH the pass (`pass.host.read`), under the containment guard a tagged GET gets. A draft whose file exists becomes a recorded read — watched on disk, which conflict detection needs, its disk version in the manifest, and a member of the write door — and one whose file does not exist becomes a recorded miss, watched and not writable. The first cut only `note()`d each draft and let it count toward the door only for a file already a member, which left a draft that outlived the server unsaveable; the maintainer's ruling the same day replaced the note with the read, since a token holder can already make a render read any contained file and reading a draft's disk bytes widens nothing. The overrides document is left out: it is no file.
- **The tree ends the pass, and so does the failure.** `/_beltype/edit/error` carries the pass id like the tree, because a failed render's misses are exactly what must be watched. A tree or failure naming any pass but the live one ends nothing and changes nothing, answered `{ ended: false }`.
- **What is watched is what the passes left.** The feed opens on the document, its entry, which no pass removes; beyond it the server never calls `watch`. `watchSet()` and core's `venueCandidates()` are deleted — the latter with its last caller. The tab never probes for a venue (the server hands it its own probe's answer, which it takes once at start or on `open`), so there are no probe misses to record there; watching the two candidates had only ever produced a `changed` the tab ignored.
- **The write door's membership is the manifest, not the posted tree.** A path is a member when the latest ended `render` pass read it, compared as Provenance keys it. A drafted file is a member because the server read it itself, so a path no render read and no draft named stays shut; a failed render adds its reads to the members instead of replacing them. Containment and the entry document's seat before any pass are unchanged. `Tree` lost `readSet` and `resources`; a tab still sending them has them ignored.
- **One line of the tab's classification moved.** A `changed` path in neither of its lists recompiles, since it can only be a location the last render missed. Without it the server would hear the missing chapter arrive and the tab would not act.

**Why the server and not the tab.** The server already serves every read, so a pass there records what was actually handed out. A session in the tab would read through the drafts, so the disk under an unsaved file could move without it hearing — the change conflict detection exists for.

## The evidence the next round builds on

*(The next round was taken the same day; see [the amendment below](#the-closure-reads-through-its-own-pass-and-the-read-set-goes).)*

For a CLI render with a venue config, a `-c` file, a `--set`, an include with a deref'd values file and a string-named plugin, the render pass's manifest (read plus noted) equals core's `pipeline.readSet` with one difference, named: **the closure's text entries**. `computeClosure` reads each stylesheet and script through the host to find its `@import`s and `url()`s, so the pass records them, and the read-set, fs-space by definition, never lists them. The spellings differ as well — the manifest is Provenance's keys (realpaths), the read-set is spelled as the host was asked. Neither list holds the virtual `#frontmatter.yaml` location; core strips it before the read-set is written. Pinned in `test/orchestrator.test.js`. Deleting the read-set bookkeeping in favour of the manifest therefore changes what the editing tools' Sources panel would list (it would gain the scanned sheets), which is the later round's question and not this one's.

## The closure reads through its own pass, and the read-set goes

*Amended 2026-09-24, round 2c, on the maintainer's rulings; recorded for the editing tools as `packages/editing-tools/DESIGN.md` 54.* Amended here rather than succeeded, because the reasoning is this record's own carried one step further: the section above found the render pass's manifest equal to core's read-set but for the closure's text files, and named that surplus as what stood between the manifest and the read-set's deletion.

**The surplus was the two-clock discriminator.** What the render READ to make the document is the recompile clock; what the closure read — the stylesheets and scripts `computeClosure` opens to follow their `@import`s and module imports — is what the emitted document reaches for, the re-serve clock. One pass could not tell them apart. So the closure reads through a host of its own: `Pipeline` takes a `closureHost` option that `assemble()` hands to `computeClosure`'s `readText`, falling back to the pipeline's host when absent, so a run with no session — `build --pdf`, the memory double, the manual test — reads exactly as before. Every dev-time embedder gives it a label of its own, `closure`: the CLI a third `readThrough` host beside `render` and `cascade`; the editing tools a second HTTP host over the same draft store, and a server that keeps one live pass per label.

**Proven, then deleted.** Before anything was removed, a CLI render on a real disk — a venue config, a `-c` file, a `--set`, an include with a `params:` values file, a string-named plugin and a stylesheet with an `@import` — showed the `render` manifest (read plus noted, canonicalized) equal to `pipeline.readSet` EXACTLY, and the `closure` manifest's reads equal to the closure's text entries' sources. Then core's record of its own reads went: `ResolvedDocument.readSet` and the instance's, `cascataHost`'s recording and `readSet` in `loadCascade`'s and `resolveConfig`'s answers (`cascataHost` stays, for `#frontmatter.yaml` and `locate`), `include.js`'s `derefFiles` (the keyscope's `derefParams` stays), the plugin loader's `loadedPaths` (resolution stays), `isMintedSet`, whose only caller was the read-set's filter, and `GenerationState`'s `readSet` — the published slice is `{ html, closure, spine }`. `scopes` stays: it is the keyscope, not bookkeeping. Core now keeps no record of what it read; an embedder that needs one asks the host it read through.

**What each embedder's lists became.**

- *The CLI.* The feed's hand-added `closureSources()` shrank to what no read opens: binary entries and `beside` entries, a font or an image listed and never read. A stylesheet edit still rebuilds — the CLI always rebuilds — and the classification is unchanged: a `cascade` location reloads the cascade, anything else rebuilds.
- *The editing tools.* The watch set is the union of both labels' manifests, and the write door admits `render` reads plus `closure` reads, which is the same set the one pass admitted. The tree's answer returns both manifests' reads and misses, spelled as the tab asked, and they are the tab's lists: the `render` reads are the Sources; what recompiles is the `render` reads and misses plus the `closure` misses; the Resources panel keeps reading the closure outlet, with its kinds and binaries. A path in both lists recompiles, and so does a `closure` miss arriving, since the closure's problems are computed at compile time — the larger action both times. A failed compile keeps the last good lists, so the rule that a path in neither list recompiles stays, for the failed render's misses, which the server watches and the tab's kept lists do not name.

**Accepted.** A failed render usually never reaches the closure, so its `closure` pass ends empty and the stylesheets leave the watch set until the next good render; an outside edit to one while the document is broken is heard by nobody, and the next good render reads it fresh. In the editing tools the single render pass had the same effect before the split, on the same files. In the CLI the hand-added closure sources used to keep the sheets watched through a failure; nothing is lost with them, because no stylesheet can mend a failed build — a closure problem only warns — so the rebuild such an edit used to cause failed the same way.

## Consequences

- **The accepted regression is closed.** A missing `@include` target is a miss of the render pass, watched; creating it rebuilds and the overlay heals (`test/orchestrator.test.js`, on a real disk, and a live `beltype` run).
- A change to a file the render read, reported while the render is running, is still turned away by the `isBuilding` guard — but the render's `end()` finds the session holding other bytes than the render used and reports it again, so it rebuilds. It used to be lost.
- A test that drives `onFileChange` by hand while writing the disk now races the feed: the pass sees the new bytes before the debounce does, and its `end()` reports them. `test/orchestrator.test.js` mutes the feed where it drives the handler.
- `loadModule`'s own probes are not recorded — a plugin name tried as `<rootDir>/extensions/<name>.js` and found in `node_modules` instead does not watch the extensions path, so creating that file later rebuilds nothing. The previous round did not watch it either.
- **The two-clock discriminator survived the read-set.** It is defined now by which pass did the reading — `render` or `closure` — rather than by a list core kept (the amendment above).
- The editing server reads through the feed as well (above). A draft that outlived the server — the draft cache is the tab's `localStorage` — is saveable: the server reads its disk bytes through the pass that names it, so it is a member of the write door from the first render after the restart (DESIGN.md 53).
