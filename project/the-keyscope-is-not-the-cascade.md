# The keyscope is not the cascade

**Status: Decided 2026-09-02.** A refusal, recorded during the BelType-on-Cascata round so the resemblance does not invite a second attempt.

## Context

`packages/core/src/plugins/include.js`'s header calls itself "the at-rule family's constitution," and inside it documents a mechanism with a cascade-shaped surface: `@include{src="./ch.md" edition="3"}` opens a **keyscope** — DITA's name for it — where an include site's attributes outrank the included file's own `params:` defaults, precisely as `spec: X` used to mean "X's keys, as if written here, weaker than mine." `CLAUDE.md` states the same shape in its own words: values are scoped along the include tree, and the cascade is scope 0 — caller beats callee. Caller-beats-callee, nearer-outranks-farther — that is also, almost word for word, how Cascata's pedigree resolves a schema chain. Two mechanisms that reduce to the same sentence when described loosely enough is exactly the situation `TABLET.md` warns against: a forced collapse of two *different* questions wearing one surface shape is the category error, and refusing it gets recorded so the resemblance doesn't invite a second attempt. This entry is that record, written before anyone attempts the collapse rather than after.

## Decision

**The keyscope stays `include.js`'s own mechanism, entirely outside Cascata. Modelling `params`, the include tree, or caller/callee precedence as a Cascata schema relationship would be a category error, and it is refused here by name.**

The two answer different questions asked at different times by different things. Cascata's cascade resolves **identity**: which schema a *document* is, walked once over a pedigree of separately-addressed, separately-pinned files, world-blind from graph-build onward, settled before any value in the document is looked at. The keyscope resolves **values inside one document's own assembly**, walked per render over the include tree that *is* the document being built — `@include` is assembly, not derivation, and `CLAUDE.md`'s own reasoning for why the merge must stay pre-parse ("CommonMark's link reference definitions and footnote definitions are document-scoped; a tree-time splice would break cross-file `[link][ref]`") only makes sense because the included files are not separate documents in Cascata's sense at all. They are text becoming one document. A schema pedigree has no concept of "this file's attributes at this particular call site," because a schema is adopted once, by identity, not spliced in per occurrence; an include tree has no other kind of node.

**The closest Cascata construct — its delegation mechanism — still is not it, and the near-miss is worth naming so the next reader does not stop at the resemblance.** Delegation grafts a schema-governed fragment into its parent's tree at graph-build time, and its own razor — a string as *data about a file* versus a string as *an instruction to load one* — is exactly the shape BelType's own `params` deref already reasoned to independently (`deref: true`, one hop, no globs, "a string inside the file is a value, never a second deref"). But delegation carries no notion of override: a fragment is grafted whole, validated positionally, and that is the entire transaction. It has nothing resembling caller-beats-callee, because a delegated fragment does not arrive with its own defaults competing against the graft site's — there is only ever one value once the graft happens. The keyscope's entire reason to exist is that an included file **does** carry its own `params:` defaults, which a caller **may** override at the call site, and that composition **must** compose down through nested includes. Delegation answers "is this data or an instruction to load," which `params` deref already borrows correctly; it does not and structurally cannot answer "whose value wins when both the caller and the callee state one," which is the keyscope's whole job.

**Refused, and why refusing it matters:** representing an include site as a schema adopting another schema, or representing `params:` defaults as a schema's `provide`, or trying to fold the keyscope into Cascata's pedigree so "one cascade" governs both. Each of these would either break the pre-parse requirement (a schema pedigree resolves after parsing has meaning, an include must resolve before it) or misrepresent what an included file *is* (not an independent, separately-identified, separately-pinned configuration, but a fragment of the very document being assembled). `CLAUDE.md`'s note on the road not taken generalizes exactly here: a flat document-wide store was refused because chapters would leak values order-dependently and silently. A flat store failed because it discarded scope; folding the keyscope into Cascata would fail for the same reason at one remove, discarding the include tree's own shape by routing it through a mechanism built to walk a different kind of tree.

## Consequences

`include.js` keeps `mintScope`, `stampValues`, and the deref logic untouched by [Cascata owns the cascade](cascata-owns-the-cascade.md); nothing in that entry's deletion of `config-schema.js` or `config-loader.js` touches this file's own reasoning, because none of it was ever really about the config cascade to begin with — the old `config-schema.js` only ever held the `deref` cell and the `params` key's territory, never the keyscope logic itself. A future session finding two "caller beats callee" mechanisms in the same codebase should read this entry before proposing to merge them; that is the entire reason it exists.
